exploratory-desktop が使えない・エラーのときは、~/.exploratory・token・アプリのログ・他の会話の記録を探したり読んだりせず、中継を自分で起動せず、利用者に Exploratory Desktop の起動を頼む（利用者のデータやプロジェクトを探すのは構わない）。

## 操作するプロジェクトを確かめる

get_environment から始める。前の会話で使ったプロジェクトに続けるときも、質問を返す前に、今も開いているかを確かめる。

開いているプロジェクトが 2 つ以上あり、利用者が対象を示していないときは、どれを使うかを聞き、書き込みの前に確認する。利用者が明示したプロジェクトを優先し、一覧の順や前の道具呼び出しで選ばない。

利用者が名指ししたプロジェクトが開いていないときは、開いていないと伝える。ほかのプロジェクトのデータで代わりに答えない。

## 進め方

依頼の大きさを見る。短い質問（例: 先月の売上合計、日別アクセス数のライン 1 枚）には、必要な計算をして答え、図表は頼まれたときに作る。複数の問いを含む分析やレポートの依頼は、下の「元の成果物があるとき」か「元の成果物が無いとき」で進め、途中で区切って報告したり、進めてよいかを確かめたりせず、最後の報告まで続ける。利用者が明示した範囲と形を守る。

利用者が「この目的変数と説明変数で線形回帰を作る」のように、使う分析と列を指定して Exploratory での実行を頼んだ場合は、下の進め方を使わない。[アナリティクス](../exploratory-analytics/SKILL.md) に従い、その分析を Exploratory で直接作る。

利用者が「年代・性別・地域でクロス集計したピボットテーブルを作って」「月別の売上をバーにして」のように、作る図表を指定して、その作成・修正だけを頼んだ場合は、属性ごとに数枚に分かれても、下の進め方を使わない。[チャート](../exploratory-charts/SKILL.md) に従い、Exploratory で直接作る。R での下計算は行わない。値の定義（どの値を満足とするか、無回答の扱い）は get_data_frame と profile_data_frame で確かめる。作った図表の違いをチャットで短くまとめる依頼も同じで、下の進め方を使わない。下の進め方を使うのは、レポート・ダッシュボードの作成を任された場合、分析そのものを任された場合（例: 「満足度を分析して」「要因を探してレポートにまとめて」）、すでにあるレポート・ダッシュボードを作り直す場合で、図表の指定があってもこのスキルで進める。

作り始める前に、このスキルのフォルダにある `steps-common.md`（Exploratory で作るときの製品の使い方と、作った後の確かめ方）と、ダッシュボードを作るなら `steps-dashboard.md`、ノートを作る・アナリティクスを作るなら `steps-note.md` を読む。

作る対象に合わせて [チャート](../exploratory-charts/SKILL.md)、[アナリティクス](../exploratory-analytics/SKILL.md)、[ノート](../exploratory-notes/SKILL.md) の必ず読む節と種類別の節を読む。加工が必要なら [加工](../exploratory-wrangling/SKILL.md) も読む。読むファイル（Read を並べる）と、これから使う create_・update_ の道具すべての get_guide(topic="…", tool="…") は、作り始める前に同じメッセージにまとめて 1 回で読み、同じものを読み直さない（現行契約・引数の規則は get_guide と道具の定義に従う）。[設定の適用](../exploratory-core/runtime-settings.md) で、この依頼の設定を確かめる。分析を始める前に [core の入口](../exploratory-core/SKILL.md) から MCP の対象指定・結果形式を読む。

### 元の成果物があるとき（作り直し）

同じ会話や作業フォルダに、すでに作ったレポート・ダッシュボード（HTML・Artifact と、それを作ったコード・データ）があり、それを Exploratory で作るよう頼まれたとき（例: 「いま作ったものを、Exploratory Desktop で作ってください」）は、元が見本で、仕事は同じものを作ること。作る前に元を最後まで読み、要素を数え上げる。形の要素（数字カードの主値と副値、図の種類・軸・区分・並び・向き・色・値のラベル、一覧の列・行数・並び順、節と見出しの順、絞り込みや切り替えなどの操作部、目次の有無（ノートは新規作成で目次が付くので、元に目次が無ければ create_note の settings に toc: false を渡す））と、文の要素（本文と結論・提案・注意書きの各項目、節の見出し、図・表ごとの説明文、図やパネルの題、表の列見出しの文言、セルの表記（単位・文言・日付の粒度）、定義や集計日の脚注（元が折りたたみでも、開いた本文として書く。`<details>` は見出ししか出ない）、数字の桁・単位・符号）の両方を数える。1 つも落とさず、同じ順・同じ形で作る。指標・区分・分母を言い換えない（例: 5 段階ごとの平均を 3 区分の割合にしない、数字カード 4 枚を表 1 枚にしない、上位 15 社の表を棒にしない）。

文の要素は元の文のまま移す。語尾・文体（だ・である／です・ます、体言止め）も、数字の桁・単位・符号も元のまま。図・表ごとの説明文はパネルや図の題に詰めず、説明文として図のすぐ近くに置き、題は元の題のままにする。

ほかのスキル・ガイド・道具の説明の既定と元の形が食い違うときは、例に挙がっていない既定も含めて、元の形を優先する。例: クロス集計に行方向の割合を足す、最新の期間の Number に前月比・前年同月比を足す、バーを降順にして値を表示する、ダッシュボードの題名に年月や数値を書かない、図の色をそろえる、図の下に説明を足す（製品の使い方で足した図は除く）、比率・係数を有効数字 3 桁にする、文の書き方。ただし、steps-common.md・steps-dashboard.md・steps-note.md の製品の使い方（ピボットテーブル・集計テーブルの緑のバー、Number はナンバー行に置く、変数重要度（重要度の図はこれ 1 つで、元の重要度の図も置き換える）・影響度とクラスタのレーダーを入れる、加工は製品のコマンドを優先する）は、元の形に関係なく守る。元が件数だけの表なら件数だけ、比較の無い Number なら比較なしで作る。元の題名・見出し・脚注の年月や数値はそのまま移す。

製品の制約で同じ形にできないものだけ形を変え、理由を報告する。制約と言えるのは、steps-common.md・steps-dashboard.md・steps-note.md の作り方と list_chart_settings・get_analytics_template・get_wrangling_command・get_guide で探して、無いと確かめたときだけ。元に無い図・節・説明・付録は足さない（製品の使い方で足した図に添える 1〜2 文の説明は除く）。足すのは steps-note.md が製品の使い方として求めるもの（変数重要度・影響度、クラスタのレーダー）だけ。R や Python で計算し直して新しいシナリオを起こさない。シナリオや計画のファイルは作らない。

計算の定義（対象の行、除外、日付の読み方、通貨の換算）は元のコード・集計・データから読み、Exploratory の加工でそろえる。作る前も作った後も R・Python（Bash を含む）で数え直さず（作った値は get_chart_data で読み、元と違えば報告に書く）、加工の式も execute_r_script で試さない（加工は create_wrangling_step の steps で足し、返り値で確かめる）。数字は作った後に主な値（Number の主値と副値）だけ get_chart_data を同じメッセージに並べて 1 回読み、元と違う値があれば報告に書く。値を元と突き合わせて原因を調べ直すのは、作成後のレビュー（フックが求めたとき）だけ行う。製品の使い方で足すもの（steps-note.md の変数重要度・影響度など）は、元の節の対応する位置に足し、元の図表は消さず、報告に「足したもの」と書く。

作り終えたら steps-common.md の「作った後の確かめ方」で元と並べて見比べ、同じに作れたもの・形を変えたもの（理由）・落としたもの（理由）・足したものを報告する。並べて見比べていない項目を「元と同じ」「元の文のまま」と書かない。並べた行のうち「同じ」以外は、すべて報告に載せる。

### 元の成果物が無いとき

Exploratory を使わずに作るときと同じように、問い・分析・構成・節の順・図の種類と枚数・Number を使うかどうか・説明の書き方を、依頼とデータに合わせて自分で決める。計算は Exploratory の加工・チャート・アナリティクスで作り、R・Python で先に計算したり、作った後に R と値を照らしたりしない（Exploratory で作れたものはその結果が正しい。値を確かめるときは get_chart_data などで Exploratory の値を読む）。読み手に見せる図表・分析・数字は Exploratory の編集できる成果物（create_note か create_dashboard）として作り、HTML や R Markdown のレポートは別に作らない。シナリオや計画のファイルは、自分の整理に要るときだけ。本文の数字は、作った図・分析から読んだ値で書く。get_guide や道具の説明にある構成・書き方の文（計算前にロードマップを返答する、差のない結果も付録に残す、作成後の点検をしない、図の下に必ず説明を書く、など）は、このスキルで進めるときは当てはめない。引数・設定・製品の制約についての文には従う。

## データを整える

集計を始める前に、(1) 比べる割合の分母（その設問に答えた人。未回答は除く。複数回答は答えた人数）、(2) 企業名などの表記ゆれ、(3) 金額の通貨が複数あるか、(4) 日付が今日より後の行があるか、を値の一覧で確かめる。表記ゆれが見つかったらそろえた列で数え、金額の通貨が複数あれば換算した列で合計する（セマンティック情報の指標が通貨ごとに分かれていても、売上全体はこうする。見つけて限界に書くだけで済ませない）。加工が要るときは [加工の共通ルール](../exploratory-wrangling/common/wrangling-common.md) の「加工を始める前に考えること」を読んでそろえる。元の成果物を作り直すときは、分母・除外・換算・日付の扱いを元の計算に合わせる。元の計算に問題を見つけても黙って直さず、元に合わせて作り（元が 0/1 の数値で計算した列は論理値にしない）、報告に書く。

下計算でも、順序付きカテゴリの Factor 化と 2 値の論理値化は同じ扱いにする。

順序を持つカテゴリ列は、加工ステップで Factor にして水準の順を明示する。連続値や日付は、カテゴリとして扱う場合に限って変換する。

2 値の列（0/1、Yes/No、TRUE/FALSE、はい/いいえ など）は、get_wrangling_command(command="mutate") で設定を確認し、mutate の expression に str_logical(列) または値と TRUE/FALSE の対応を明示した論理式を指定して、論理値（logical）に変える（NA はそのまま保つ）。「あり/なし」などの文字列ラベルへの置換はせず、表示に日本語のラベルが要るときはチャートの表示名で付ける。

自由記述や記録の意味を読む加工（話題の分類・感情の判定・要約）は、get_ai_function_presets で現在のプリセットを確かめ、create_wrangling_step の params.aiPreset（指示を調整するときだけ params.aiPrompt も指定）で AI 関数の列を作る。作り方は [AI 関数](../exploratory-ai-functions/SKILL.md)（AI 関数の出力の書き方）を読む。キーワード・正規表現・case_when などの条件式で意味を推し量って分類しない。プリセットの取得や AI 関数の実行が失敗したら、条件式や自作の指示文へ黙って切り替えず、失敗と理由を利用者に伝える。分類は、先に原文の値の一覧（profile_data_frame など）を見て分類名を決め、最初から params.aiPrompt に分類名の一覧を書いて固定する（プリセットのままだと同じ内容に別の名前が付き、やり直しになる）。この列は下計算より前に作ってよい。分類後は結果を原文数件と照合し、分類の方法・照合の件数・重複の扱いを記録してから、話題別の人数や件数と結果指標を集計する。

## R の結果の返し方

集計表は通常の行・列を持つ data.frame を最後の式として返す。問い・切り口・対象・件数・分母・指標値・比較の差・不確かさ・警告を対応させ、数値・日付・論理・文字列の型と必要な全計算を保持する。表全体を toJSON して1セルに包む方法を通常の分析結果の返却には使わず、head(out) を最終結果にして残りの行を捨てない。

結果をまとめるのは、意味・型・観測単位がそろう場合に限る。その場合は問いや結果種別の列で対応を示せる。異種集計の列の和集合を作り、存在しない列をNAで埋めた広い表へ縦結合する形を通常の返却には使わない。正当な欠測や、同じ意味・型・観測単位の指標行は保持する。複数の計算へ分ける場合は、各表の未取得ページを回収してから次の計算へ進み、必要な分析を削らず、共通計算の重複を避ける。

返答の dim・cols・col_types・preview_rows・truncated・redacted_msg と result_retrieval を確認する。初回previewは既定100行。必要な続きは同じ元の r_script と同じ dataFrameId、retrieve_result=true、offset、limitで取得する。最初にdataFrameIdを省略した場合は省略を維持する。取得用の別 idempotency_key を使い、計算時のキーは変更しない。offsetは0以上、limitは1〜1,000、既定100。result_retrieval.limit=100は既定の案内で、上限ではない。next_offset、受信行数、全行数で回収範囲を確認する。列指定の引数はないため、必要な列の整形は初回のR式で行う。

保持されるのは、このプロジェクトのRセッションにある最新の計算済み表だけ。次のR計算・保存・R再起動より先に必要な全ページを取得する。out等のローカル変数が次の呼出しに残る前提にせず、get_executionを同期R結果の回収に使わない。失効・対象不一致はエラーとして扱い、再取得では再計算しない。必要な再計算は別の実行として記録する。

JSONや長文そのものが必要な依頼では、その目的と全文を保ち、値を無断で切り捨てない。現在の取得は行単位で、1セル内部はページングできないため、この場合は通常表の返却量改善とは分けて扱う。

R の対象には、取得した id を `dataFrameId` に明示して `execute_r_script` を使い、その対象の最後のステップを参照するローカル変数 `df` から計算する。ID とステップ名から R 名を組み立てず、ls() で名前を探さない。列・ステップは get_data_frame、行数・分布は profile_data_frame で確かめる。

下計算では元のデータを上書きせず、対象を絞る計算は一時的なデータで行う。指標ごとに使える全対象を集計し、あるモデルで使えた行だけに他の集計もそろえない。NA や空の結果を差がない証拠として扱わない。
