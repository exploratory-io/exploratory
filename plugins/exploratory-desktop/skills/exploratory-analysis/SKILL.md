exploratory-desktop が使えない・エラーのときは、~/.exploratory・token・アプリのログ・他の会話の記録を探したり読んだりせず、中継を自分で起動せず、利用者に Exploratory Desktop の起動を頼む（利用者のデータやプロジェクトを探すのは構わない）。

## 操作するプロジェクトを確かめる

get_environment から始める。前の会話で使ったプロジェクトに続けるときも、質問を返す前に、今も開いているかを確かめる。

開いているプロジェクトが 2 つ以上あり、利用者が対象を示していないときは、どれを使うかを聞き、書き込みの前に確認する。利用者が明示したプロジェクトを優先し、一覧の順や前の道具呼び出しで選ばない。

利用者が名指ししたプロジェクトが開いていないときは、開いていないと伝える。ほかのプロジェクトのデータで代わりに答えない。

## 進め方

依頼の大きさを見る。短い質問（例: 先月の売上合計、日別アクセス数のライン 1 枚）には、必要な計算をして答え、図表は頼まれたときに作る。複数の問いを含む分析やレポートの依頼は、次の 4 つの順で進める。4 つは一続きの作業なので、途中の段で区切って報告したり、次へ進んでよいかを利用者に確かめたりせず、手順 4 の報告まで続ける。利用者が明示した範囲と形を守る。

この 4 手順は、データから何が言えるかを考え、結論や打ち手をレポートにまとめる依頼に使う。この場合は、手順 1 のシナリオの (a)〜(d) を書き終えるまで `list_analytics_templates` と `get_analytics_template` を呼ばない。

利用者が「この目的変数と説明変数で線形回帰を作る」のように、使う分析と列を指定して Exploratory での実行を頼んだ場合は、この 4 手順を使わない。[アナリティクス](../exploratory-analytics/SKILL.md) に従い、その分析を Exploratory で直接作る。

1. まず、R で計算しながら、依頼に答えるシナリオを書き、今の作業フォルダに `<題名>_シナリオ.md` として保存する。この段だけで仕事が終わるつもりで、依頼主にそのまま出せる本文として書く。あとの手順（Exploratory で作ること）は考えず、作りやすさに合わせて分析・図・文章を減らさない。読み手は分析の専門家ではない依頼主とする。読み手が最初から最後まで迷わず読み、結論を信頼し、次に何をするかを決められるものにする。データを広く見て、依頼の問いに答えるのに必要な分析を選ぶ。シナリオは次の節を持つ。(a) 依頼の問いを番号付きで分ける（依頼文の文ごとに 1 つ以上。ダッシュボードなら、見る人が最初に答えを知りたい順）。(b) 結論を 3 行以内。(c) 問いごとの答えと根拠の数字。数字はすべて R で計算したものを使う。問いごとに少なくとも 1 つ、結論を覆しうる切り口（層の分け方・期間・分母の取り方）を R で確かめ、確かめた結果を書く。(c2) 深掘りの問い。本筋の答えを出したら、依頼で聞かれている結果（例: 満足度）について、答えを深めたり打ち手を具体的にしたりする問いを少なくとも 2 つ足す（例: どの層でその結果が低いか、その結果と関係のある態度・イメージの項目や自由記述から見える理由）。依頼で聞かれていない別の結果（例: 満足度を聞かれたときの推奨度や購入）には広げない。答えは R で計算した数字で書く。(d) 打ち手（何を・誰に・どの順で・期待する効果の大きさ）。打ち手は結論から出し、1 つずつ (c)・(c2) で示した根拠の数字を添える。根拠のない打ち手は書かない。依頼で聞かれている結果との関係を確かめていない打ち手（例: 評価が低い項目、自由記述で多かった話題）は、書く前に R でその関係を確かめ、確かめた数字を (c2) に足す。確かめて差が確認できなかった項目（ほかの項目をそろえると差が消えるもの、差が確かとは言えないものを含む）は、打ち手にも優先順位にも入れない。「第三候補」「あとで検討」としても書かない。打ち手の対象（項目と層）は、すべて (b) の結論にも同じ順番で書き、結論にないものは打ち手に出さない。打ち手の文にも統計の言葉（回帰、P 値など）を使わない。結論や打ち手を弱める注意書き（因果は断定できない、小さく試して、など）は書かない。優先順位は、確かめた効く大きさの順にする。効く大きさは統計の言葉を使わず、比べ方で書く（例: その評価が低い人と高い人で、満足と答えた割合を並べる）。(e) 見せる図の一覧（(c) と (c2) の両方の図を含める）。図ごとに、答える問いの番号・図の形・なぜその形かを書く。(f) 分析の確かさと限界。R の計算は、手元に R があれば Rscript、なければ execute_r_script で行う。R の図（ggplot2 など）は、データの形を確かめるために自由に描いてよい。描いた図は PNG で今の作業フォルダに保存し、データと文字の言語に合うフォントを指定して文字が化けないようにする。ただし (e) の図の一覧は R の図を元にせず、問いごとに Exploratory のアナリティクスの出力やチャートから選ぶ。(a)〜(d) を書いたら、使う分析の出力一覧を `list_analytics_templates` と `get_analytics_template` で見てから (e) を書く。状況をつかむダッシュボードでは、直近の動きと傾向が一目でわかる期間と粒度を選ぶ。HTML のレポートや R Markdown は作らない。
   本文は、統計に詳しくない依頼主が、何が分かり、次に何をするかを読み取れる言葉で書く。各節では答えを先に示し、誰の何を比べた数字なのかが分かる根拠を添える。統計用語は本文に出さず、必要な内容は、回答した人・比較したもの・見られた違いを表すふだんの言葉に言い換える。分析方法や統計指標の説明は、ノートの末尾の補足にまとめる。採用しなかった案の結果（例: 別の分け方・別のグループ数にしたときの図）や、統計の指標が並ぶ表も補足に置き、本文には採用した理由を短く書くだけにする。本文に置く図と表には、1 つずつ、すぐ下に何がわかるかを 1〜2 文で書く。ノートでは、割合を 1 つだけ示す Number チャートを使わない。ある・ない、はい・いいえのような区分の割合は、すべての区分の人数と割合が並ぶピボットテーブルで示す。分類名や社内の呼び名は、初めて読む人にも対象が分かる名前にし、同じものは最後まで同じ語で呼ぶ。比喩や名詞の並びで済ませず、誰が何をしたか、何がどう違うかを自然な日本語で書く。数字は、回答の集計、分析からの見込み、仮定を置いた試算のどれなのかが、その文で分かるように書く。一文では一つのことを伝え、意味が変わらない範囲で短くするが、分析の範囲・節・図の数は減らさない。
   時系列の最新の期間の値（毎月の NPS・売上・ライセンス数・その月の顧客数や注文数）を Number で示すときは前月比・前年同月比などを付け（最新の期間が途中（今月・今年）のときは、終わった直近の期間どうし（先月と先々月）を比べるか、前の期間も同じ日付までに絞って比べる（式の例は steps-2-4.md の「比較する期間」の段落）。そろえにくいからといって、頼まれた指標の Number を外さない。）、全体を見る数（全回答者数・全従業員数）には付けず、手順 1 の R に無くても手順 3 の Exploratory で付ける。
   R のチャートを保存したら、画像を開いて、日本語など多バイトの文字が正しく表示されているか（文字化けしていないか）と、文字が重なって読めなくなっていないかを確かめ、問題があれば直して保存し直す。
   シナリオを保存したら、このスキルのフォルダにある `steps-2-4.md` を読み、手順 2〜4 に進む。手順 2〜4 の「HTML のレポート」は、手順 1 のシナリオ（R の計算結果を含む）に読み替える。

作る対象に合わせて [チャート](../exploratory-charts/SKILL.md)、[アナリティクス](../exploratory-analytics/SKILL.md)、[ノート](../exploratory-notes/SKILL.md) の必ず読む節と種類別の節を読む。加工が必要なら [加工](../exploratory-wrangling/SKILL.md) も読む。細かな規則は、道具の説明が指定する get_guide(topic="…", tool="…") も操作前に読む（現行契約・引数の規則は get_guide と道具の定義に従う）。[設定の適用](../exploratory-core/runtime-settings.md) で、この依頼の設定を確かめる。分析を始める前に [core の入口](../exploratory-core/SKILL.md) から MCP の対象指定・結果形式を読む。

## データを整える

集計を始める前に、(1) 比べる割合の分母（その設問に答えた人。未回答は除く。複数回答は答えた人数）、(2) 企業名などの表記ゆれ、(3) 金額の通貨が複数あるか、(4) 日付が今日より後の行があるか、を値の一覧で確かめる。表記ゆれが見つかったらそろえた列で数え、金額の通貨が複数あれば換算した列で合計する（セマンティック情報の指標が通貨ごとに分かれていても、売上全体はこうする。見つけて限界に書くだけで済ませない）。加工が要るときは [加工の共通ルール](../exploratory-wrangling/common/wrangling-common.md) の「加工を始める前に考えること」を読んでそろえる。

この節の加工は手順 3 で行う。手順 1 の R では、順序付きカテゴリの Factor 化と 2 値の論理値化は同じ扱いにする。

順序を持つカテゴリ列は、加工ステップで Factor にして水準の順を明示する。連続値や日付は、カテゴリとして扱う場合に限って変換する。

2 値の列（0/1、Yes/No、TRUE/FALSE、はい/いいえ など）は、get_wrangling_command(command="mutate") で設定を確認し、mutate の expression に str_logical(列) または値と TRUE/FALSE の対応を明示した論理式を指定して、論理値（logical）に変える（NA はそのまま保つ）。「あり/なし」などの文字列ラベルへの置換はせず、表示に日本語のラベルが要るときはチャートの表示名で付ける。

自由記述や記録の意味を読む加工（話題の分類・感情の判定・要約）は、get_ai_function_presets で現在のプリセットを確かめ、create_wrangling_step の params.aiPreset（指示を調整するときだけ params.aiPrompt も指定）で AI 関数の列を作る。作り方は [AI 関数](../exploratory-ai-functions/SKILL.md)（AI 関数の出力の書き方）を読む。キーワード・正規表現・case_when などの条件式で意味を推し量って分類しない。プリセットの取得や AI 関数の実行が失敗したら、条件式や自作の指示文へ黙って切り替えず、失敗と理由を利用者に伝える。分類は、先に原文の値の一覧（profile_data_frame など）を見て分類名を決め、最初から params.aiPrompt に分類名の一覧を書いて固定する（プリセットのままだと同じ内容に別の名前が付き、やり直しになる）。この列は手順 1 の R の計算より前に作ってよい。分類後は結果を原文数件と照合し、分類の方法・照合の件数・重複の扱いを記録してから、話題別の人数や件数と結果指標を集計する。

## R の結果の返し方

集計表は通常の行・列を持つ data.frame を最後の式として返す。問い・切り口・対象・件数・分母・指標値・比較の差・不確かさ・警告を対応させ、数値・日付・論理・文字列の型と必要な全計算を保持する。表全体を toJSON して1セルに包む方法を通常の分析結果の返却には使わず、head(out) を最終結果にして残りの行を捨てない。全表を返せば、実行側が計算済み表を保持して表示用previewだけを制限する。

結果をまとめるのは、意味・型・観測単位がそろう場合に限る。その場合は問いや結果種別の列で対応を示せる。異種集計の列の和集合を作り、存在しない列をNAで埋めた広い表へ縦結合する形を通常の返却には使わない。正当な欠測や、同じ意味・型・観測単位の指標行は保持する。複数の計算へ分ける場合は、各表の未取得ページを回収してから次の計算へ進み、必要な分析を削らず、共通計算の重複を避ける。

返答の dim・cols・col_types・preview_rows・truncated・redacted_msg と result_retrieval を確認する。初回previewは既定100行。必要な続きは同じ元の r_script と同じ dataFrameId、retrieve_result=true、offset、limitで取得する。最初にdataFrameIdを省略した場合は省略を維持する。取得用の別 idempotency_key を使い、計算時のキーは変更しない。offsetは0以上、limitは1〜1,000、既定100。result_retrieval.limit=100は既定の案内で、上限ではない。next_offset、受信行数、全行数で回収範囲を確認する。列指定の引数はないため、必要な列の整形は初回のR式で行う。

保持されるのは、このプロジェクトのRセッションにある最新の計算済み表だけ。次のR計算・保存・R再起動より先に必要な全ページを取得する。out等のローカル変数が次の呼出しに残る前提にせず、get_executionを同期R結果の回収に使わない。失効・対象不一致はエラーとして扱い、再取得では再計算しない。必要な再計算は別の実行として記録する。

JSONや長文そのものが必要な依頼では、その目的と全文を保ち、値を無断で切り捨てない。現在の取得は行単位で、1セル内部はページングできないため、この場合は通常表の返却量改善とは分けて扱う。

R の対象には、取得した id を `dataFrameId` に明示して `execute_r_script` を使い、その対象の最後のステップを参照するローカル変数 `df` から計算する。ID とステップ名から R 名を組み立てず、ls() で名前を探さない。列・ステップは get_data_frame、行数・分布は profile_data_frame で確かめる。

下計算では元のデータを上書きせず、対象を絞る計算は一時的なデータで行う。指標ごとに使える全対象を集計し、あるモデルで使えた行だけに他の集計もそろえない。NA や空の結果を差がない証拠として扱わない。

ダッシュボードでは、チャート・ノートの共通手順にある個別画像確認より、steps-2-4.md 末尾の全体画像確認を優先する。get_dashboard_image で全体を1回確認し、get_chart_image は使わない。
